# WS53 SWD 调试

使用 `riscvcs` 后端，经 AP0 使能调试，再从 AP1 访问 RISC-V Debug Module。
J-Link 使用 libjaylink 的底层 SWD 传输，不经过 SEGGER DLL 的 RISC-V 连接流程。
已验证应用调试及 `reset run` 后的启动、再次暂停和 GDB 重连；复位时先将 CPU 切回晶振，见下文。
不提供 WS53 Flash 烧录、擦除或 LiteOS 线程解析。

## 连接与 GDB

连接 VTref、GND、SWDIO、SWCLK；板卡供电且固件已配置 SWD 引脚。
默认 100 kHz，加载目标文件前可用 `set ADAPTER_SPEED 1000` 修改。
仅连接一只驱动 SWD 的探针；两只探针在线时必须指定序列号。

```sh
./build-ws53/src/openocd -s tcl -f interface/jlink.cfg \
  -c "adapter serial 23121310; bindto 127.0.0.1" \
  -f target/ws53.cfg -c "init; halt"
```

另开终端，使用 WS53 SDK 中的 `riscv32-linux-musl-gdb`：

```gdb
file /path/to/matching-firmware.elf
target extended-remote 127.0.0.1:3333
info registers pc sp ra
x/8bx $pc
stepi
hbreak *0xADDRESS
continue
detach
```

`file` 只加载电脑端符号，不写目标。源码调试要求 ELF 与板上固件匹配；本次没有匹配的
应用 ELF，验证的是指令级调试。不要执行 `load` 或套用 WS63 的 Flash/RTOS 工具。
GDB 默认强制硬件断点；显式 OpenOCD ITCM 软件断点也经过了命中、跨越与恢复验证。

## 实现

- 参照 HiSpark Studio `resources/connect/CFBB/ws53/connectCore.JLinkScript`：
  vendor DP bank 0xE 写 1，AP0 `0xF0000038` 写 1，使用 AP1；与 WS63 AP0、3322 value-3 初始化不同。
- AP1 IDR `0x74770001` 为 AHB-AP。AP 查找比较类型位时同时掩码 IDR 与枚举值，
  失败路径及退出路径平衡 AP 引用。使用明确的 CSW/TAR/DRW 事务。
- AP0 使能地址在参考脚本中读回 `0xFFFFFFFF`，不以它作为连接成功判据；以 AP1 DM 检查为准。
- CPU progbuf 内存访问逐事务检查错误，验证宽度、对齐、范围和增量，保存并恢复临时 GPR。
- WS53/WS63 共用安全的断点跨越及复位触发器重装。修复观察点停止后显式指定新 PC 继续时
  错误预单步的问题；单步时暂时关闭所有触发器，软件断点恢复原指令后执行并重新安装。
- `reset halt` 使用 ndmreset 并确认暂停，清除程序缓存，重装断点；不伪报运行状态。

WS63 功能来自 [HiSpark PR #22](https://gitcode.com/HiSpark/hs-openocd/pull/22)，
作者 Padhia Luo，参考提交 `1aff54e6c5259de553fce2e8cf781bd1d71426be`。
旧 `WS63-jlink.cfg`、`WS63-swd.cfg` 也共用修复实现，保留自动 init/halt 和默认 `WS63_FLASH=0`。
WS63 的 Flash/RTOS 功能说明见 [ws63.md](ws63.md)。

### reset run 持续 WAIT 的原因与修复

WS53 的 `NDMRESET` 将 CPU 带回复位入口，但保留 MCU 时钟选择。应用使用 PLL 时，
直接放行 ROM 会在重建 PLL 的过程中关闭 CPU 正在使用的时钟，CPU 和 AP1 随之停止响应。
实测 ROM `0x11ADC` 向 `0x57008540` 写入 `0xB040`（原值 `0x3040`），
即置位 `CMU_FNPLL_SIG[15]`；在该指令前暂停正常，单步执行后立刻出现持续 SWD WAIT。
这是复位时钟状态不匹配；增加 SWD 重试无法恢复已停止的 CPU 时钟。

修复在复位释放后、CPU 仍停在入口时，按 SDK
`drivers/chips/ws53/clock_recover/acore/acore_clock_recover.c` 的
`acore_switch_pll_clock(false)` 顺序配置**非当前使用**的 MCU 时钟通道为无分频 XO，
先使能该通道，再切换 normal/sleep mux，并检查实际通道状态。
只修改 MCU 通道的相关字段，不关闭 PLL、不修改 ROM、不下载 RAM 跳板。
配置或读回失败就返回错误并保持暂停；WS63 不执行这段 WS53 专用逻辑。

```tcl
reset halt
reg pc          ;# 0x10000
step
reg pc          ;# 0x10004
reset run
sleep 5000
halt
reg pc
step
resume
```

`reset halt` 同样准备 XO，随后直接 `resume` 也能安全通过 ROM 的 PLL 初始化。
实测覆盖当前 A 板和固件；这不等于完整的芯片上电复位，也不保证恢复任意外设或低功耗状态。

## 重复运行检查

在专用 OpenOCD 会话中开启本地 Tcl 端口 6666，不要同时连接 IDE/GDB。
下面测试暂借 ITCM `0x20000` 的 32 字节及当前 DTCM 栈以下的 32 字节。
输出目录必须不存在；程序先保存恢复快照，再写 RAM，结束时核对恢复，失败时保持暂停。
需要确认当前固件使用 SDK 对应的 ITCM/DTCM 布局；不要在其他核/芯片上运行。

```sh
python3 contrib/ws53/check_debug.py --port 6666 --output /tmp/ws53-check-new
python3 contrib/ws53/test_config.py /path/to/built/openocd
# 会复位应用，丢失运行中的 RAM 状态；不烧录
python3 contrib/ws53/check_reset.py --port 6666 --output /tmp/ws53-reset-new
```

通过的原始恢复快照保留在测试机，不提交板卡 RAM 数据到公共仓库。

## 构建

```sh
git submodule update --init jimtcl src/jtag/drivers/libjaylink
./bootstrap nosubmodule
mkdir -p build-ws53
cd build-ws53
../configure --enable-jlink --enable-internal-libjaylink --enable-ftdi --disable-werror \
  CFLAGS='-O2 -g -Wno-error=int-conversion -Wno-error=incompatible-pointer-types -Wno-error=implicit-function-declaration'
make -j8
```

本分支保留锁定的子模块版本，Jim Tcl 已有命令名称对象的引用保护。
替换原有只打印成功而不写 Flash 的 WS63 驱动，并修复 CMSIS-DAP 枚举辅助函数中的 void 返回值。

本机新版 GCC 对既有其他芯片驱动需要上述兼容诊断选项；这不代表旧代码警告已经消除。
